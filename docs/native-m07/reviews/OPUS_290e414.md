## 3. New M7 functional findings (all in new M7 code; none is a regression of earlier accepted scope)

### N-1 — HIGH — A rejected shortcut in onboarding makes Skip/Finish and normal quit fail forever

**Trigger**
1. On the onboarding Shortcut step, record a shortcut that the OS rejects (for example one that is already registered).
2. The core returns `{"ok":false}` from `llm-config-set` (`tezbar-core/src/ai/mod.rs:667-675` → `platform.rs:232-261`).
3. Onboarding correctly shows "Shortcut unavailable. Your previous shortcut is unchanged."
4. The user then presses **Skip tour** or **Finish**.

**Call sites**
- `onboarding.rs:463-480` enqueues `Edit::Global{raymesHotkey}` into the shared WriteQueue. On `ok:false`, `store.rs:436` → `queue.finish(token,false)`, which retains a durable failure for that intent.
- `onboarding.rs:185-210` Finish/Skip uses the **all-owner** `store.drain()`. The pump returns `Err` while `failures() > 0` (`store.rs:455-459`).
- `onboarding.rs:212-215` Retry calls `store.retry()`, which **replays the rejected shortcut**. It is rejected again.
- `app.rs:468` quit uses `shared_settings.drain_with`, so quit is cancelled. The onboarding error says "Retry saved changes" (`app.rs:520`), which replays the same rejection.

**Reproduction.** `opus_probe_conflicting_shortcut_does_not_block_finish_or_skip` (`probe1.log`), on the real `Onboarding` entity and production `SettingsStore`. The transport returns `ok:false` only for patches that contain `raymesHotkey`:

```
shortcut_error=Some("Shortcut unavailable. Your previous shortcut is unchanged.") kept="Alt+Space"
skip_error=Some("Could not finish saving. Retry to complete onboarding.")
retry_error=Some("Could not finish saving. Retry to complete onboarding.")
finished=0 hasCompleted=true close/quit barrier=Err("Couldn't save Settings. …")
```

**Effect**
- On first run the user cannot leave onboarding. Skip, Finish and Retry all fail, and normal quit is refused. Note that `hasCompletedOnboarding` **was** written durably, but `Finished` is never emitted.
- The only way out is to notice that recording a different, valid shortcut supersedes the failed intent. Nothing in the UI suggests this.
- The same retained rejection blocks closing the Settings window when the hotkey is recorded there.

**Fix**
- Treat a validation rejection (`ok:false` from the hotkey route) as a settled, non-retryable outcome for that intent, with an error to the owner only. Either:
  - add a tri-state `finish(token, Saved|Rejected|Failed)` in WriteQueue, where Rejected records no retryable failure; or
  - add `SettingsStore::discard(owner, Key::Global("raymesHotkey"))` and call it from both hotkey recorders on rejection.
- Finish/Skip should settle only onboarding's own `hasCompletedOnboarding` intent (`drain_owner` semantics). Leave the all-owner barrier for close and quit.

**Required regression:** this probe. Then Skip emits `Finished` exactly once, and the close barrier is `Ok`.

### N-2 — MEDIUM — Failed operational mutations are retained forever, replayed by Retry, block close/quit and use up admission

**Trigger.** Any `recoverable_write()` operation fails for a lasting reason. The set is large (`request.rs:153-190`):
- Voice delete: file in use or permission denied.
- Knowledge AddRoot: the folder vanished, giving "Choose an existing folder" (`knowledge/db.rs:475`).
- Remove or Uninstall of an extension that was already removed.
- AcceptReview or SetTool against stale data.

**Call sites**
- `store.rs:284-286`: a failure goes into `failed`. Only operations that have a `mutation_scope` are ever pruned (`store.rs:123-127`), and delete/add/remove/uninstall/accept have none.
- `store.rs:100-112`: Retry re-queues every entry, and they fail again.
- `store.rs:184-193`: `failures()` counts these entries, so `drain`, close and quit fail (`store.rs:455`, `app.rs:468`, `app.rs:1351-1366`).
- `store.rs:115`: `failed.len()` counts toward the 15-slot admission bound. Each repeated click adds another entry.
- There is no discard path.

**Reproduction** (`probe1/2.log`)
- `opus_probe_failed_operational_delete_is_retryable_but_never_dischargeable`: the close barrier is `Err` before and after 3× Retry; `voice:model:delete` was sent 4 times; `failures=1`.
- `opus_probe_repeated_failed_operations_exhaust_admission`: after 15 failing deletes, an unrelated Voice select is refused with "Settings actions are still finishing. Retry." It sends 0 `set-selected` calls, and `failures=15`.

**Effect**
- The Settings window cannot be closed and normal quit is cancelled until that operation succeeds. If it never succeeds, the only way out is force-quit.
- Repeated attempts stop Settings from admitting any durable operation: account, device, contribution, voice select, permission or URL.
- TS showed the error and moved on.

**Fix**
- Report operational failures through their own completion. Do not retain them in the close/quit barrier. If retention is wanted, then:
  - dedupe by target;
  - exclude them from admission capacity;
  - expose an explicit **Dismiss** next to **Retry**;
  - never replay `ok:false` rejections.

**Required regressions:** the two probes above.

### N-3 — MEDIUM — Every Settings save waits on the all-owner drain, so unrelated failures cancel the user's next action

**Trigger.** Any retained failure from another owner or operation, such as N-2, a failed launcher picker write, or onboarding's N-1. The user then:
- toggles a setting;
- presses **Sign in with GitHub** (Copilot);
- presses a permission **Request**;
- presses **Open Permissions**; or
- presses **Quit** in Advanced.

**Call sites**
- `settings/mod.rs:748-800`: `flush()` awaits `store.drain()`. Any `Err` clears `after_save` (`:789`) and sets `CLOSE_ERROR`, even when the user's own intent was saved.
- After-save actions are gated the same way: `SignIn` at `:1704-1721`, `Permission` at `:1465`, `OpenPermissions` at `:1804`, `Quit` at `:1802`.
- The launcher picker already does this correctly with `drain_owner(owner)` and `owner_failure_count`.

**Reproduction** (`probe1/2.log`)
- `opus_probe_unrelated_failed_operation_blocks_copilot_signin`: after one failed Voice delete, Sign in sends **0** `github-device-start` and shows "Couldn't save Settings…".
- `opus_probe_successful_toggle_reports_failure_after_unrelated_operation_failed`: the toggle is persisted (`memoryEnabled=false`), but the view reports "Couldn't save Settings…".

**Effect**
- Copilot sign-in, permission requests, Open Permissions and Settings-Quit are silently dropped.
- Every successful edit is labelled as failed.
- This contradicts the requirement "Sign-in saves correct provider first" and the owner-scoped design already shipped for the picker.

**Fix**
- `flush(after)` should wait for settlement of this owner's intents admitted up to the click, using revision-targeted `drain_owner` semantics. For Sign-in, wait only for the Copilot field intents.
- Decide success from `owner_failure_count(owner)` plus this owner's validation entries.
- Keep the all-owner `drain_with` only for close and quit.

**Required regressions:** the two probes above.

### N-4 — LOW (P3) — Race: an owner drain can hang behind a pump that is exiting

**Call sites**
- `store.rs:419-426`: the pump decides to exit under the state lock, but finishes outside it.
- `store.rs:222-234`: `start_worker` decides whether to start a new pump from `JoinHandle::is_finished()` / `try_lock`.
- In the window between those two, an `enqueue` plus `drain_owner` sees the old pump as alive and does not spawn one.
- `drain()` has the same window between its `pending()` check and releasing the worker lock (`store.rs:251-255`).

**Reproduction.** `opus_probe_owner_drain_cannot_strand_behind_an_exiting_pump` (multi-thread runtime, 20,000 enqueue+`drain_owner` cycles with a 500 ms timeout): **1/20000** stranded in run 1 and **6/20000** in run 2.

**Effect.** The launcher model picker stays in `model_saving` until some other action starts a pump (Settings save or quit). The model menu cannot submit.

**Fix.** Track pump liveness inside `State`. The pump clears `running` in the same critical section where it decides to exit. `start_worker` checks and sets `running` under that lock and spawns when it is false. Remove the `try_lock`/`is_finished` decision.

### N-5 — LOW — A bare "F" key is accepted as the global Tezbar shortcut

**Call site:** `settings/view.rs:1573`. `parts.is_empty() && !k.key.starts_with('f')` accepts any key name that starts with `f`, including the plain letter `f`. Onboarding reuses the same function.

**Reproduction.** `opus_probe_plain_f_key_is_not_a_global_shortcut`: `accelerator("f") = Some("F")`.

**Effect.** If the OS accepts the registration, the plain letter F becomes the global hotkey. TS allows only modifier combinations or F1–F24 (`SettingsView.tsx:183`).

**Fix.** Match `^f([1-9]|1[0-9]|2[0-4])$`.

### N-6 — LOW — The unresolved durable-failure message disappears on any action

**Call site:** `settings/mod.rs:1463`. `action()` clears `self.error` first. There is a single error slot, and a config-read error (`:887-891`) also overwrites it.

**Reproduction.** `opus_probe_tab_switch_hides_unresolved_durable_failure`: before a tab switch the view shows "Couldn't save Settings…"; after it, the error is `None` while `store.failures()=1` (`probe2.log`).

**Effect.** The user loses sight of an unsaved change until close fails. This contradicts "config read/UI errors do not clear durable write failure".

**Fix.** Show a separate, persistent store-failure line derived from `store.failures()`. Transient and validation errors keep their own slot.

### N-7 — LOW — Current Theme, release channel and Knowledge depth/speed are never shown

**Call sites**
- Theme buttons have no selected state or role (`view.rs:212-218`).
- Channel buttons are raw lowercase strings with no state (`:276-278`). `update_channel` is loaded by `m7_load_channel`, but no view reads it (grep: only `set_update`).
- Knowledge depth and speed buttons have no state (`:645-660`).

**Effect.** Users and assistive technology cannot tell the current choice. This is a TS parity gap: those were segmented controls and selects.

**Fix.** Use the shared segmented control with `aria_selected` and the current value.

### N-8 — LOW (traced) — The retained onboarding content keeps a 250 ms timer for the rest of the session

**Call sites**
- `settings/mod.rs:406-421`: `activate` starts an unconditional 250 ms loop until the entity is dropped.
- `settings_integration.rs:82-106`: `finish_onboarding` keeps `self.onboarding`, which also keeps its embedded `SettingsContent`.

**Effect.** After a user visits the AI, DeepSearch or Permissions step, the hidden launcher wakes 4 times a second forever. There is no I/O, because ticks are gated, but this works against the background-idle budget. The Settings window content does the same while open.

**Fix.** Start and stop the timer from `set_visible` and from the knowledge/device/account need, or drop the onboarding entity after `Finished` once origin lookup no longer needs it.

### N-9 — LOW (traced) — A second launcher size/zoom change during a pending layout write is rejected and leaves a failure behind

**Call site:** `app/m7.rs:490-500`. While `layout_pending` is set, a new effect fails immediately with "Layout save is still finishing" and becomes the latest barrier entry. When the first write completes it is no longer current, so it never clears that entry.

**Effect**
- The newer zoom is not applied.
- The parent shows "Could not save Settings".
- Close and quit fail until Retry.

The window is the duration of the disk write, so this is rare.

**Fix.** Coalesce: keep the latest requested layout and apply it when the pending write finishes, instead of failing it.

### N-10 — LOW (traced) — A late core start after a failed start hides the visible launcher

**Call site:** `app/m7.rs:100-114` together with `app.rs:96-107`. After a failed start, `boot=Ready` and the launcher is shown with Retry. A later successful `start_core` reaches `m7_ready`. Because `decided` is false, it hides the visible launcher and runs the gate again. It may also mount onboarding.

**Effect.** The user's open launcher and query are reset after they press Retry. This contradicts "no late interactive reset".

**Fix.** If the launcher has already been shown (fail-open), run the gate without `hide()`, and defer onboarding to the next show. Alternatively, record that the gate was decided as fail-open.

## 4. Checked and found correct (M7)

- **One executor.** `run()` builds one `SettingsStore` on the `CoreClient` (`app.rs:1516`), and its clones go to Settings, Onboarding (embedded content plus its own owner) and the launcher picker. `Launcher::new` still constructs a private store, but nothing calls it in production (dead API; nit).
- **Fresh canonical merge.** `durable_config()` reads `CoreContext.config` in `spawn_blocking`. The projection (`llm-config-get`) is never used as the merge base.
- **Transient contributions.** Merge skips edits to extension-managed providers, and the core strips `_extensionId` before persisting. The view hides credential fields for managed providers.
- **Removal, recreation and discovery.** Covered by the existing production-queue fixtures, which pass in my 187 run.
- **Picker settlement.** It does not wait for a held download, and it ignores peer failures through `owner_failure_count`. The exceptions are N-4 and the earlier note in N-3.
- **Secrets.** Request `Debug` output is redacted, with no logs in M7 files (grep). The contribution display is redacted by the model. Secret slots are opaque. Password fields clear after save. Sign-in edits only Copilot fields.
- **Voice.** Every listed model has a Select radio that never downloads. Cancel is per model and is an interrupt with its own ticket. Delete and progress use the existing channels.
- **Close lifecycle.**
  - The shell acknowledges first.
  - `close_failed` is fenced by generation, so a late error never reaches a new shell.
  - `SettingsFinish` rechecks the store and barrier at the destruction boundary.
  - The three-second fallback applies only when the close was not acknowledged.
  - The launcher is restored before the window is removed.
  - The `after_close` destination is routed after a successful close.
- **Boot gate.** It runs once after a successful coreReady, with one 400 ms retry and fail-open (fixture). N-10 is the exception.
- **Navigation.**
  - Settings intents are acknowledged once and do not replace launcher navigation.
  - Content dedupes by nonce.
  - `OpenSurface("settings…")` reaches Settings through one path; the earlier double-open is removed.
- **Updates.** Update actions are queued in the typed `UpdateInbox`, which has no production consumer until M11. The UI says "Update requested" and never fabricates an install result; the consumer belongs to M11. Legacy cache cleanup refuses with honest copy.
- **No new processes.** No new process, `unsafe`, WebView or unbounded channel appears in M7 files. Render does no requests or spawns, except the standards note in §6.

## 6. Design and standards judgment

No screenshots were taken. These points come from reading against §5 of the spec only; manual visual acceptance remains open.

**D-1 (Medium quality) — implementation copy in Settings**
- Knowledge buttons are labelled with internal root UUIDs (`"Toggle folder {id}"`, `"{id}: inherit"`, `view.rs:669-690`).
- Raw JSON is dumped for Knowledge status (`:696`), AI extension details, import preview and project review (`safe_display`, `:1612`).
- Extension and command buttons carry raw IDs (`"Save {id} {index} {field}"`).
- Voice shows raw `"{downloaded} / {total} bytes"`, which renders `" / null"` for an unknown total, and raw status tokens (`:618`).
- Depth, speed and channel use lowercase enum tokens.

§5.6 rejects generic and implementation copy. Port the TS labels (selects, formatted bytes, named folders).

**D-2 — Zoom grid.** Zoom is a grid of 26 identical buttons from 75% to 200% (`view.rs:122-129`), which is the rejected "identical button grid" pattern. Use a stepper or segmented control.

**D-3 — Confirmation dialog**
- All destructive confirmations say "Confirm this action?" with a plain "Confirm" button (`view.rs:1442`): remove provider, uninstall, reset secrets, remove extension.
- It is generic copy, does not name the target, uses no danger tone, and is inline at the root rather than a focused sheet.

**D-4 — Retry on every error.** "Retry saved changes" is attached to every error (`view.rs:1461`), including validation errors ("Enter a positive width…") and discovery errors. This is misleading; see also N-6.

**D-5 — Content width (traced).** The §5.1 content max width (610, or 850 for AI) is not applied; the body is the full 920 px window minus 24 px padding.

**D-6 — Pin glyph.** The pin uses the text character `⌖` (`utilities/view.rs`). Use the shared SVG pin glyph from the icon set.

**Spec checks found clean.** No gradients, glass, purple-blue defaults, side stripes, badges, ALL-CAPS or skeletons were found in M7 files. Tokens come from `tezbar_ui::tokens`, and the selected tab uses `pill_strong`. The roles are reasonable: tablist/tab, roving tab index, password options, radio for voice. Screen-reader and contrast acceptance remain unproven.

**Standards**
- The Extensions tab creates `TextInput` entities and subscriptions inside render (`view.rs:960-990`, via `self.field`) and calls `replace_silently` during render. This is not I/O, but it is state mutation in render, and the fields are never removed for the session. Move preparation to the completion of the Installed/Schema reads.
