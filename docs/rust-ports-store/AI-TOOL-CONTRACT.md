# Native extension tools in Tezbar AI

Design proposal, 2026-11-20. Tezbar can discover tools from a verified installed Rust package without starting it. Add an optional manifest declaration and one host-to-extension method, then feed those declarations into the existing Rust agent tool table. Start the existing package process only when an approved call needs it. A normal command launch or an independently registered background contribution may already have started the process.

## Proposed first version

**Package declaration.** Add optional `aiTools` to schema 3, protocol 1. An absent field gives an empty set. A nonempty array opts the package into `ai.tools.v1`. No new reverse capability is needed. Use a bounded, strict descriptor with a package-local name, title, description and full input schema. An optional `preferenceKeys: [string]` defaults to empty and may name only declared extension-wide preferences. Include that projection in the reviewed descriptor hash. For example, this object is one element of Chrome's proposed array.

```json
{
  "name": "search-history",
  "title": "Search History",
  "description": "Search Chrome history for the given profile.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "profile": { "type": "string" }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

Validate a maximum of 128 descriptors per package, unique bounded ASCII component names, nonempty bounded display strings, a bounded total manifest consistent with the existing 1 MiB discovery reader, schema compilation and wire projection. Keep the 128-entry limit shared with MCP. Use a single deterministic name allocator across built-ins, MCP and process registrations. Preserve existing names and cap/collision behavior, give process entries stable names derived from canonical owner and original tool name, and resolve model names only through the run's table. An explicit source `tools` array supplies labels and entry points. Derive the actual schema from each pinned handler's TypeScript input/defaults, documenting intentional validation differences. Implement corresponding Rust input types and require fixture tests for the agreement.

**Discovery and trust.** The host owns registration. On metadata refresh, enumerate supported installed canonical packages and verify only candidates, off the async/UI thread. Cache descriptors by profile, active directory and manifest digest. Recheck on package changes, profile changes and invocation. Catalog entries, replaced IDs, ZIP filenames, source snapshots and child announcements cannot add entries. Enforce the package's declared OS as well as executable target availability. This excludes the macOS-only Chrome/Brew Windows development ZIPs from Windows advertisement.

Offer a package-level AI-tools enable control and per-tool disable control in AI settings. Store the reviewed package pin and choices in a profile-local native-package section, separate from imported MCP connection records. New or changed package pins need review. Include the target, manifest digest, executable digest and descriptor hash in the pin. A same-version repack must invalidate approval. Uninstall clears active grants and outstanding calls. Changing credentials, workspace or profile while approval is open invalidates that call's account binding. Keep any credential/account revision used for that check host-private and opaque. Do not persist tokens, secret-derived identifiers or credentials in this registry. For the first version, prompt once for each invocation through the existing cancellable approval UI. Show the trusted owner, tool, effect and scrubbed arguments. Disable the remember control by passing no MCP allowance identity. Display names, source annotations, a read-only label and available credentials never confer approval.

**Host routing.** Replace the MCP-specific fields of `Entry` with a tagged target, keeping model-facing descriptor, hash and label common. Preserve the existing MCP branch intact. Suggested Rust shapes below are internal.

```rust
enum ToolTarget {
    Mcp { extension: String, connection: String, client: Arc<Client>, resource: Option<ResourceOp> },
    Process { owner: CanonicalPackageId, pin: PackagePin, tool: String },
}
```

Give `AiCore` a narrow internal handle supporting package tool discovery and invocation. Construct it from the existing `ExtensionsCore.native` and configuration context in `crates/tezbar-core/src/lib.rs::configured`. Avoid a second process manager or a general channel accessible to extensions. Public UI RPCs should only edit the user's native-tool choices or answer existing pending approvals. After the whole batch is validated, resolve the snapshot target, verify the live owner/pin, tool enablement, run selection, profile and schema, then request approval. Repeat the live checks after approval and before writing the request. Serialize the final admission with disable/uninstall/reinstall generation changes and cancel in-flight work on revocation. Do not hold settings or install locks across approval, process startup or the running tool.

**Handshake and call.** A tool-capable child lists `ai.tools.v1` in hello. The host offers it in `initialize.hostFeatures` only for validated declarations. A ready child acknowledges it with `features: ["ai.tools.v1"]` among any other negotiated features and an `aiToolNames` array populated from its compiled dispatch. Require exact set equality with the declarations when enabling this feature. Treat a missing/mismatched acknowledgment as tool-unavailable in the selected package, preserve its ordinary commands, and suppress/diagnose the failed feature for that pin. An old host ignores optional metadata and an old child receives zero new requests. Static discovery can list reviewed declarations before the first handshake. Product status should distinguish these from runtime-verified handlers.

```json
{"type":"request","id":"h:<uuid>","method":"ai.tools.call","params":{"name":"search-history","arguments":{"query":"example"},"preferences":{}}}
{"type":"response","id":"h:<uuid>","result":{"value":[{"title":"Example","url":"https://example.com/"}]}}
```

Use strict `ToolCall { name, arguments, preferences }` and `ToolResult { value: JsonValue }` types. The host supplies the original local name and the subset of current **declared extension preferences** required by that owner. Load these only after approval. Project `registry::preferences(..., None)` onto the selected descriptor's validated `preferenceKeys` before sending. It currently merges saved unknown keys and can contain a nested command map. Keep this trusted parameter separate from model arguments and export neither it nor the call envelope to stage events, transcripts, durable background records or logs. Use a secret-aware scrubber for returned values, errors and approval displays, including known active credential values and authorization headers. Return simple errors using the existing JSONL error envelope. Bound the serialized result before encoding and at host receipt, using the agent's 64 KiB result budget. Convert strings to text and other JSON values to compact JSON in a tool-result block. Parse neither embedded markup nor returned data as commands. Documents, images or file bytes that cannot fit this result contract need a later typed contract and explicit acceptance.

**SDK and lifetime.** Add default-empty `Extension::tool_names()` and default-unsupported `Extension::call_tool(ctx, name, arguments)`. Put the owner-projected preferences in an operation-local context for the handler. Validate handshake, compiled name membership and strict request shape in the runner. Reject pre-ready/unnegotiated calls. Allocate an operation scope that ends on reply, cancellation, failure or shutdown, and keep session-only APIs unavailable. Reuse the existing request cancellation token and wait on the AI run cancellation, slot revocation and deadline around `Process::call`. Before sending on a warm slot, compare the process package directory and verified pin with the approved binding. The RPC ID scopes replies to that live process. A model cannot provide an extension ID, session ID, generation, capability grant or credential. Existing reverse calls still go through the host's package-level typed allowlist. New tool APIs do not imply an OS sandbox or a narrower per-request privilege boundary. Tool code must own and cancel any HTTP/helper tasks, close handles, and avoid detached work and credential persistence. Timeouts after transmission produce an unknown-outcome result for side effects. Never replay them automatically.

## Provider and confirmation parity

The first version can carry ordinary JSON tool arguments/results. It does not itself implement mention selection, resource reads, source-specific confirmation previews, OAuth or bundled AI skills.

- **Mentions and resources.** Keep the five source mention searches off the ordinary tool list until their intended composer path is supported. In a later negotiated feature, declare search IDs and the owning resource reader, add typed composer-search and selected-resource-read requests, and return bounded title/URI rows. Issue an opaque selection handle bound to the verified owner, tool, active pin, account, profile and exact URI. Require this handle and current authorization on read. Validate the selected scheme, route and identifiers again in the extension. Linear returns `linear://users/…`, `issues` and `projects` routes. Slack returns `slack://users/…` and `channels` routes with workspace scope. Apply cancellation/debounce when queries change. `ai/ext/resources.rs::extension_resource` and `ai-extensions:composer-items` provide existing UI/policy patterns. The current MCP reader uses a listed resource or template and a live MCP client. A general URL fetch or full resource enumeration would change what these two upstream providers do.
- **Confirmations.** Static reviewed descriptions and scrubbed raw arguments allow a first host-owned prompt for simple actions. Where the source resolves identities or displays a specific before/after preview, keep that tool out of parity counts until there is an equivalent review. For example, Linear resolves an issue identifier to a title/ID before deletion and Slack previews archive targets and canvas changes. If needed, add a separately negotiated, bounded read-only prepare operation with user authorization for any protected lookup. Bind the preview's resolved target and argument digest to a one-shot execution approval, recheck before effect and reject stale previews. A handler's self-asserted read-only annotation cannot authorize a write.
- **Account and domain behavior.** Implement each Rust handler, default, authorization scope, account boundary, result serializer, paging/error semantics and confirmation against its pinned upstream file. Mapping an entry to a GPUI view or preserving a file under `upstream/` cannot execute it. Track managed OAuth, skill instructions, provider-specific files/images and platform acceptance independently.

## Implementation and verification order

1. Add the manifest validator, fixture manifests and installed candidate scan. Test legacy absence, duplicate/malformed names, schema bounds/remote references, wrong OS, invented catalog rows, missing executables, digest mismatch and trusted ZIP mismatch. Listing an unrelated profile, launcher or composer must start zero Rust children and zero Bun workers for this feature.
2. Implement the additive runner feature and wire fixtures in the standalone SDK. Exercise old/old, old/new, new/old and new/new peers, undeclared names, acknowledgment mismatch, pre-ready call, a successful value, bounded malformed output and a late reply after cancellation. Existing SDK/session and launcher fixtures must still work. Update protocol docs and pin each adopting port to the actual tested SDK revision.
3. Wire discovery, settings, approval and the internal native target into the existing agent loop. Extend `crates/tezbar-core/src/ai/ext/tests.rs` and `extensions/process_tests.rs` using fake provider, real fixture child and private temp profiles. Assert whole-batch failure before effects, global name collisions, profile allowlists, denied/expired approvals with zero launches, projected preferences, no secret in any recorded prompt/event/transcript/error, current-pin checks after approval, concurrent disable/uninstall, process crash/deadline with one observed send and normal idle cleanup. Check a real agent turn through the provider wire adapter and verify the successful tool result reaches the following turn.
4. Adopt ordinary handlers incrementally. For Chrome, replay its source evals and compare private fixture profile output. For Linear/Slack, match exact calls and returned values against loopback fixtures, including authentication failure, pagination, partial completion and cancellation after a write. Record source count, ported count, announced count, successfully invoked count and real-platform acceptance separately. Register only tested implementations. Add mention/provider and source-preview fixtures as separate milestones. Brew needs no AI registration.
5. Before integration use the project's local quality gates, `pnpm typecheck` and `pnpm test`, plus the focused Rust/SDK suites. Platform acceptance uses the supported OS, an isolated profile and the tested package digest. This document records source inspection and proposed tests. It makes no claim of executable, account or release acceptance.
